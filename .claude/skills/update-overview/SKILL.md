# update-overview

`docs/プロジェクト概要.html` は目的・思想・現在地・将来対応・構成図をまとめた**正本**。人が読む 1 枚であり、`build.py` が自動欄を書き込む場所であり、フェーズ（`data-phase`）の正本でもある。壊さずに更新するための手順。

## 発火条件

- フェーズを切り替える（ユーザーの承認後。下の「フェーズの切り替え」）
- 方針・設計原則が変わった
- エピック（まとまった機能）が完了した
- ロードマップ（将来対応）の時期・内容・状態が動いた
- 環境構成（環境の追加・削除・構成図の変更）が変わった
- 打合せ記録・課題の決定やタスクの期限が動いた → 手で書かず `build.py` を回す（自動欄が更新される）
- ユーザーが「概要を更新して」「現在地を直して」等と言った

## HTML の構造（触ってよい場所）

固定セクションごとにコメントマーカーが 1 対ずつある。**編集は必ずマーカーの内側だけ**。

| マーカー | 内容 | 編集 |
|:--|:--|:--|
| `updated` | 最終更新日（`YYYY-MM-DD`） | 更新のたびに今日へ |
| `purpose` | 1. 目的・背景 | 目的が変わったときだけ |
| `principles` | 2. 思想・設計原則 | 原則の追加・変更 |
| `phase` | 3. 現在地: フェーズと一言（`data-phase` と `.name` と `.word`） | `data-phase` と `.name` は `phase.py --set` だけが書く。手で触るのは `.word`（次の一手）だけ |
| `open-issues` | 決めてほしいこと（open の課題） | `build.py` が自動生成。**手で編集しない** |
| `milestones` | 次の節目（ロードマップの日付 + タスク・課題の `due`） | `build.py` が自動生成。**手で編集しない** |
| `recent-decisions` | 直近の決定（打合せ記録の決定行 + 閉じた課題の `## 決定`） | `build.py` が自動生成。**手で編集しない** |
| `task-snapshot` | タスクの状況 | `build.py` が自動生成。**手で編集しない** |
| `roadmap` | 4. 将来対応: 表（時期 / 内容 / 状態 / 関連 ID） | 行の追加・状態変更。時期に日付（`YYYY-MM-DD` か `YYYY-MM`）を書いた行は「次の節目」に出る。チームに見せてよい日付だけを書く |
| `map` | 5. 構成図と環境の入口: テキスト図 + 環境表 | 構成変更時。URL・秘密は書かず「環境情報.md 参照」 |
| `history` | 6. 更新履歴: 表（日付 / 更新箇所 / 要点、新しい順） | 更新のたびに先頭へ 1 行 |

`<style>`・`<script>`・`<nav>`・マーカーの外側・マーカーそのものは**不可侵**。

- 決定を概要に載せたいときは、打合せ記録の `## 決定` に書くか、課題を `new.py … --decided "<決定>" --to "<落ち先>"` で記録してから `build.py` を回す（`task` スキル）
- 未決を載せたいときは課題を起票する（`--kind 課題`）。期限を載せたいときはタスク・課題の `due`

## 手順

1. **全体を Read する**（部分読みで済ませない。マーカーの位置と既存の書き方を把握する）
2. **対象マーカーの内側だけを Edit する**。`old_string` にマーカー行を含めて一意にする。自動欄 4 つは触らない
3. **現在地 ⇔ 将来対応の整合を取る**。完了した項目は `roadmap` から落とし、`history` へ「完了」として記す。`phase` の一言と `roadmap` の直近行が矛盾していないか読み直す
4. **`updated` を今日の日付にし、`history` 表の先頭に 1 行足す**（日付 / 更新箇所 / 要点）
5. **自動欄を再生成する**
   ```bash
   python3 docs/案件/01_タスク管理/build.py
   ```
6. **検査する**
   ```bash
   python3 scripts/check_skeleton.py --overview
   ```
   マーカー対の欠落・重複、外部 `src` / `href`、`data-phase` の値を検出する。秘密らしき文字列は `check_skeleton.py --docs` が概要 HTML と設計書をまとめて見るので、続けて実行する。失敗したら直してから終える
7. **変更点を 3 行で報告する**（どのセクションを・何から何へ・関連 ID）

## フェーズの切り替え

フェーズは `Sketch` / `Build` の 2 つ。フェーズごとの仕組みの厳しさは `python3 .claude/hooks/phase.py --table` が正本（文書に表を写さない）。

| 項目 | 決め |
|:--|:--|
| 誰が決めるか | **AI が判断して切り替える。確認は挟まない。** 切り替えたら報告で 1 行伝える |
| いつ切り替えるか | Build へ: 関係者向けの資料や確認依頼を出し始めた／設計書（01 以外）を足した／実装や設定変更を始めた（最初の実装タスクへの着手を含む）、または SessionStart に Build の目安が出た。Sketch へ戻す: 情報集めに戻ったとAIが判断した（大きなスコープ変更・作り直しなど） |

1. **切り替える**（手で HTML を編集しない）
   ```bash
   python3 .claude/hooks/phase.py --set Build
   ```
2. **phase ブロックの `.word`（次の一手）と `history` に 1 行を書き**、`build.py` → `check_skeleton.py --overview`
3. **切り替え時の見直し（一度だけ。全部を埋めない）**
   - Build へ: `harness` スキルの観点カタログを 1 回通して見て、候補を `docs/ハーネス台帳.md` に書く。特に「品質ゲート（テストの実行方法）」「権限」「危険操作」「外部接続」「文脈注入」。雛形のままの設計書のうち、**これから触る領域の文書だけ**節見出しの下に 1 行ずつ書く（残りは未記入のまま）。打合せ記録の `→ 候補: NN §n` のまま残る決定は `python3 scripts/check_drops.py` で一覧が出るので、正本に入れて `→ 反映済: NN §n` に書き換える（`sync-design-docs` スキル）。本番のマイグレーション・デプロイのコマンドが決まっていれば、観点「危険操作」として 05 §9 と `permissions.deny` に足す（候補として台帳へ）。初回の本番リリースが決まったら、05 §9 の「提案」行を決定か見送りに倒し、07 §5・§6 と runbook の索引を確認する
   - Sketch へ戻す: 何もしない（厳しさが下がるだけ）
4. **報告**: 旧 → 新、切り替えた理由、見直しで出た候補の件数

## 書き方の決めごと

- 一文は短く。「現在地」の一言は 1〜2 文
- 時点の状態ではなく**決定した事実**を書く（「検討中」を長く残さない。検討中は課題 md へ）
- URL・ID・パスワード・鍵は書かない。環境の入口は「名前 / 用途 / 正本の所在（環境情報.md §n）」の形にとどめる
- `claude-starter` 等の生成時プレースホルダが残っていたら、そのセクションを編集するついでに実名へ置き換える

## 禁止事項

- マーカーの外側・`<style>`・`<script>`・`<nav>` を編集する
- 自動欄（`open-issues`・`milestones`・`recent-decisions`・`task-snapshot`）を手で書き換える（`build.py` に上書きされる。決定は打合せ記録か課題に書く）
- `data-phase` と `.name` を手で書き換える、ユーザーの承認なしにフェーズを切り替える（`phase.py --set` を使う）
- 概要 HTML に秘密の実値や公開しない日程を書く（公開しない日程は `案件情報.md` §3）
- `history` を更新せずに本文だけ変える
- `check_skeleton.py --overview` を通さずに終える
