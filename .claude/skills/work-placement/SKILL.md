# work-placement

「作業」を始めるときに、**どのタスクの作業として、どこで作業し、生み出した成果物をどこへ置くか**を最初に決める入口スキル。置き場所の細部は `.claude/rules/docs-management.md`（`docs/案件`）と `.claude/rules/work-area.md`（`.work`）へ委譲し、ここでは「着手時の判断」と「振り分けの原則」だけを扱う。

なぜ入口で決めるか: 後から「このファイルどこに置こう」と考えると、ルート直下に散らかしたり、履歴に残すべき一次資料を捨ててしまったりしやすい。着手時に紐づけ先タスクと振り分け先を決めておくと、迷いなく正しい場所へ置ける。

## 適用タイミング

ファイルを生成・編集しうる作業に着手する**前**。

- コードやドキュメントの「実装」「修正」「対応」を依頼されたとき
- 調査・設計・検証の結果を何らかのファイルに残すとき
- 検討記録・提出資料など一次資料を作るとき
- 検証スクショ・スキャン結果など、あとでタスク md から参照する証跡を残すとき

「これはどのタスクの作業だろう」と一瞬でも思ったら、そこが発火点。明確な作業指示ではない依頼（質問への長文回答・比較表・ドラフト）でファイルを作るときは `scratch` スキル。

## ステップ

### Step 1. 紐づけ先タスクを最初に確定する

`docs/案件/01_タスク管理/open/` の既存タスク（`<ID>_タイトル.md`）のどれに当たるかを見る。

**どのタスクか曖昧なときは、推測で進めず AskUserQuestion で必ず確認する。** 紐づけ先を取り違えると一次資料が迷子になり、後から履歴を辿れなくなる。これがこのスキルで最も守ってほしい点。

- 既存タスクに当てはまる → そのタスク md を作業の起点にする（経緯・判断は本文へ追記）
- 新しいまとまった作業である → ユーザーに確認のうえ `task` スキルで起票する
- タスクに紐づかない一時作業（純粋な実験・確認のみ）→ `scratch` スキルで `.work/一時/` に完結させる
- 打合せ記録 → `docs/案件/02_打合せ/`（決定・未決・宿題の各行に落ち先を書く。`pickup` スキル）、相手への確認事項 → 課題を起票し、相手向けの文面が要れば `docs/案件/確認依頼一覧.md` に ID 付きで。専用の置き場がある種別はそちらへ

### Step 2. 実ソースは実体を直接修正する

コード・設定・既存ドキュメントの修正依頼は、**実ファイルそのものを編集する**。`docs/案件/` に作業用コピーを作ってそこを直す、という回り道はしない（実体と乖離した死蔵コピーが生まれる）。

`docs/案件/` に置くのは「修正したコードそのもの」ではなく、その修正に至った**経緯・判断・成果のまとめ**（タスク md 本文へ追記）。

### Step 3. 成果物を振り分ける

2 つの問いで置き場が決まる。

> **① 半年後にこのファイルを読み返す価値があるか？**
> **② それを Git（共有）に載せてよいか？**

| ① | ② | 置き場 | 命名 |
|---|---|---|---|
| Yes | Yes | タスク md と同じフォルダ（`docs/案件/01_タスク管理/open/` 等） | `<ID>_内容_YYYYMMDD.拡張子` で併置 |
| Yes | No（大きい・生証跡・顧客名を含む） | `.work/証跡/<ID>_内容/` | タスク md から「証跡: <パス>」で名指しする |
| Yes | No（受領した一次資料そのもの） | `.work/機密/<ID>_内容/` | 同上 |
| No | — | `.work/一時/YYYYMMDD_用途/` | `scratch` スキル |

- 横断的に参照される設計判断は `docs/設計書/decisions/` の ADR へ昇格する（`.claude/rules/docs-management.md`）
- **迷ったら `証跡/`。** `一時/` は予告なく消える。`証跡/` は邪魔になるだけで済む
- `.work/証跡/`・`機密/` に置いたものを後から `一時/` へ退避しない（参照が黙って切れる）。移動が要るときは `.work/README.md` の対応表を同じ作業で更新する

### Step 4. 終わったらタスク md に戻す

作業の結論・変更点・残課題をタスク md の該当セクション（過去の経緯・参照情報）へ追記する。フェーズや方針が動いたなら `update-overview`、環境や関係者が変わったなら `update-env-info` を同じ作業で実行する。

区切りで拾いもの（決定・未決・あとでやること・ハーネス候補）があれば `pickup` スキルで「反映済・タスク・未決」のどれかに落とす。残課題を会話やタスク md の本文にだけ残して終えない。

## 禁止事項

| 禁止 | 代わりに |
|---|---|
| 紐づけ先タスクが曖昧なまま推測で進める | AskUserQuestion で確認 |
| 実ソースの修正依頼に対し `docs/案件/` 内のコピーを作って直す | 実体を直接修正し、経緯をタスク md へ |
| 残す価値のある一次資料（設計判断・検討記録・提出物）を `.work/一時/` に捨てる | タスク md 併置か `.work/証跡/` |
| タスク md から参照する証跡を `.work/一時/` に置く | `.work/証跡/<ID>_内容/` |
| `.work/` 配下を移動したのに `.work/README.md` の対応表を更新しない | 同じ作業で対応表へ 1 行 |
| 使い捨ての確認用画像・ログを `docs/案件/` に混ぜる | `.work/一時/YYYYMMDD_用途/` |
| プロジェクトルート直下・`.work/` 直下・`.work/一時/` 直下に成果物を直接置く | 上の表のいずれか（hook が止める） |
| 秘密の実値をタスク md や `docs/` に書く | `環境情報.md` を参照させる |
