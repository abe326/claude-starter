# audit-design-docs

設計書は打合せ・タスク・実装が先に進むと構造的に置き去りになる。`sync-design-docs` が「変えたその場」で追随させるのに対し、このスキルは**節目にまとめて突き合わせ、修正候補のリストを作る**。リストアップと修正を分けるのは、根拠の薄い書き換えで正本を壊さないため。

## 発火条件

- 「設計書を見直して」「総点検して」「乖離を洗い出して」「設計書は最新か確認して」
- `docs/案件/02_打合せ/` に記録を追加した後（決定が動いた可能性）
- エピック・フェーズが完了した後
- SessionStart の「設計書の要確認: N 本」に「N 日更新なし」の文書が含まれるとき

## 原則

1. **最新の決定が正**。記述が食い違ったら日付の新しい決定を採る
2. **実装が正しいとは限らない**。「設計書 ≠ 実装」はどちらが最新の決定かを日付・根拠で判断し、判断できなければ「要確認」に倒す
3. **指摘には根拠が必須**（ファイル:行・タスク ID・コミット SHA・打合せ日付のいずれか）。裏取りしていない指摘は載せない
4. **リストアップと修正を分ける**。成果物は見直しリスト。本体はユーザーの採否後に `sync-design-docs` で直す
5. **課題として open の論点（本文の「（未決 <ID>）」）を不足・乖離として指摘しない**（未決は意図して未決。未決の正本は課題 md で、設計書の `## N. 未決` 節は固定文 1 行）

## 指摘の書式

種別は 5 つ: **不足**（書かれるべき決定が無い）/ **乖離**（記述が実態とずれている）/ **陳腐化**（役目を終えた記述が残っている）/ **内部矛盾**（設計書同士・同一文書内の食い違い）/ **要確認**（白黒つけられず人の判断が要る）。

各指摘は 6 項目で書く。

| 項目 | 内容 |
|:--|:--|
| 種別 | 上の 5 つのいずれか |
| 対象 | `docs/設計書/<ファイル>:<節>` |
| 内容 | 何がどうずれているか（1〜2 文） |
| 根拠 | ファイル:行 / タスク ID / SHA / 打合せ日付 |
| 修正の方向 | どう直すか（採否判断ができる粒度） |
| 確度 | 高 / 中 / 低 |

## 手順

1. **DOC タスクを起票する**（点検 1 回 = タスク 1 つ。過去の点検タスクへ追記しない）
   ```bash
   python3 docs/案件/01_タスク管理/new.py 文書 "設計書棚卸 YYYY-MM"
   ```
2. **全読 + 鮮度スカウト**。`docs/設計書/` を全部読み、最古の最終更新日 T を求めて T 以降の動きを集める
   ```bash
   python3 scripts/docs_freshness.py --list        # 最終更新の一覧。最古を T にする
   python3 scripts/check_drops.py                  # 落ち先なし・候補のまま・決着済みの未決参照（観点 1〜3 の手がかり）
   ls docs/案件/02_打合せ/                          # T 以降の打合せ記録
   ls -t docs/案件/01_タスク管理/closed/ | head -30  # T 以降にクローズしたタスク
   ls docs/案件/01_タスク管理/open/                  # 進行中の論点
   git log --oneline --since=<T>
   git log --oneline --since=<T> -- docs/設計書/decisions/
   ```
3. **9 観点で突き合わせる**。観点ごとに Agent ツールで **sonnet** のサブエージェントを並列に立ててよい（読み取り専用。出力は 6 項目形式）。並列手段が無ければ順に全部踏む。中間出力は `.work/証跡/<DOC-ID>_棚卸_YYYYMMDD/観点N_<名前>.md`

   | # | 観点 | 突き合わせ先 | 典型的な発見 |
   |:--|:--|:--|:--|
   | 1 | 打合せ | `docs/案件/02_打合せ/`（T 以降）の決定行と落ち先 | 未反映の決定、落ち先が `→ 候補: NN §n` のままの決定が正本に入ったか（Build へ移るときの棚卸しで拾い直す） |
   | 2 | クローズ済みタスク・課題 | `01_タスク管理/closed/`（T 以降）。課題は `## 決定` の落ち先 | 「未実装」「検討中」の陳腐化、決着済みの課題を本文が「（未決 <ID>）」で指したまま |
   | 3 | open タスク・課題 | `01_タスク管理/open/` | 新方針の未反映、同じ論点の課題が重複 |
   | 4 | ソース | 影響マップの行ごとに `git log --oneline --since=<T> -- <glob>` | 設計書が知らない変更 |
   | 5 | ADR | `docs/設計書/decisions/` と索引 | ADR と本文の食い違い、索引漏れ |
   | 6 | 概要 HTML | `docs/プロジェクト概要.html` | 目的・現在地・構成図の乖離 |
   | 7 | 設計書内の整合 | 相互参照の実在、用語 ⇔ `CLAUDE.md` §6、技術スタック ⇔ §5 | リンク切れ、用語の揺れ |
   | 8 | ハーネス整合 | `.claude/`（rules・skills・hooks）の参照先が実在するか | 廃止済みファイルへの参照 |
   | 9 | 環境・関係者 | `環境情報.md`・`案件情報.md` の構成と設計書の記述（**値は転記しない**） | 環境の増減、役割の変更 |

4. **全件反証する**。指摘ごとに根拠のファイル・行・タスク・コミットを実際に開いて裏取りする。崩れた指摘は棄却し、棄却理由を残す（再点検時の重複防止）
5. **見直しリストを書く**: `docs/案件/01_タスク管理/open/<DOC-ID>_見直しリスト_YYYYMMDD.md`
   - 要約（件数・種別内訳・要確認の一覧）→ 種別ごとの指摘（6 項目）→ 棄却した指摘（理由付き）
   - **顧客と共有するリポでは** `.work/証跡/<DOC-ID>_棚卸_YYYYMMDD/見直しリスト.md` に置き、タスク md から参照する
6. **チャットには要約と要確認だけ**を出し、採否を仰ぐ。本体はこの時点で書き換えない。採用分は `sync-design-docs` で反映し、DOC タスクをクローズする

## 決めごと

- T はファイル間で割れる。**最古**を採って取りこぼしを防ぐ
- 観点 4 のソース突合は影響マップ（`docs/設計書/README.md`）の行を単位にする。表に無いディレクトリに変更が集中していれば、それ自体を「影響マップの不足」として指摘する
- サブエージェントの出力はそのまま採らず、手順 4 で必ず裏取りする

## 禁止事項

- 根拠なしに指摘を載せる（手順 4 を省略しない）
- リストアップと同時に設計書本体を書き換える
- 実装を無条件に正として「設計書が間違い」と断定する（要確認に倒す）
- 「最終更新」表記だけで鮮度を判断する（表記自体が古いことがある。`docs_freshness.py` の結果も参考値）
- 観点を打合せだけ・ソースだけに絞る（9 観点を全部踏む）
- 秘密の実値（URL・ID・鍵）を見直しリストや証跡に写す
