# sync-design-docs

`docs/設計書/` は設計・方針の正本。ソースが先に進み、設計書が置き去りになる乖離を「同じ作業の中で」潰すためのスキル。**要否判定 → ソースを読む → 決まったことを 1 行拾う → メタ行と改訂履歴 → 下流 → 検査**の順で、飛ばさない。

問いは「矛盾しないか」ではなく「**この変更で何が決まったか**」。雛形のままの設計書は、矛盾しないのではなく、まだ何も書かれていないだけ。

「何を変えたら、どの設計書を見るか」の正本は `docs/設計書/README.md` の「## 変えたもの → 一緒に直す正本」表（影響マップ）。hook（`design_docs_reminder.py`・`pickup_check.py`）と検査（`scripts/docs_freshness.py`・`check_skeleton.py --docs`）も同じ表を読む。
表で書きにくい判定（先勝ち・除外・フォールバック）は、任意の差し込み口 `.claude/hooks/impact_map_local.py` の `targets(rel_path) -> list[str]` に書ける（hook が表の結果に足す）。置いたら表にそれを指す行を 1 行書く（`check_skeleton.py` が見る）。定義はユーザーの承認後（`harness` スキル）

## 発火条件

- ソース（認証・権限・セッション、スキーマ・マイグレーション・モデル、デプロイ・CI・コンテナ、テスト、依存関係）を変えた
- `docs/案件/02_打合せ/` に打合せ記録を追加した、`docs/設計書/decisions/` に ADR を追加した
- Edit/Write 直後に PostToolUse hook が `[設計書追随] … 更新候補: …` を出した
- ターンの終わりに Stop hook が `[拾う] … 実装: <パス> → <設計書>。決まったことを 1 行` を出した
- SessionStart が `設計書の要確認: N 本` を出した（N>0）
- push・コミットの前
- 「設計書を更新して」「設計書に反映して」「設計書は最新?」「設計書とずれてない?」
- **Sketch の間は hook 起点では発火しない**（hook は `[設計書候補]` を出すだけ。決まったことは `pickup` スキルで 01 §1・§3 に 1 行、ほかは落ち先に `→ 候補: NN §n`）。ユーザーの依頼・コミット前は Sketch の間でも従来どおり。フェーズは `python3 .claude/hooks/phase.py`

## 構造（設計書 1 本の約束）

| 場所 | 内容 |
|:--|:--|
| 2 行目 | 鮮度メタ行 `> 最終更新: YYYY-MM-DD（<タスクID>: 要点）／ 対象: <glob を・区切り> / repo@<short-sha>`。ソース非依存の文書は `対象: 案件情報.md §1・打合せ記録`（repo@ なし）。任意で ` ／ 鮮度: 90日` |
| 本文 | 決定した事実。詳細仕様はコードが正本なので、設計書は方針・境界・理由にとどめる。決まっていない箇所は「（未決 QA-01）」で課題を参照する |
| `## N. 未決` | 固定文 1 行（未決の正本は課題 md）。書き足さない。この文書に関わる未決は `python3 scripts/check_drops.py --refs NN` |
| `## 改訂履歴` | 表（日付 / ID / 要点。新しい順）。必須 |

## 手順

1. **鮮度を機械で見る**
   ```bash
   python3 scripts/docs_freshness.py
   ```
   「ソース変更あり」「未コミット変更あり」「N 日更新なし」「メタ行なし」の文書が候補の第一群。
2. **何が変わったかを集める**
   ```bash
   git status --porcelain
   git diff --name-only <メタ行の sha>..HEAD      # 無ければ HEAD~5..HEAD
   ls -t docs/案件/02_打合せ/ | head -3
   ls docs/設計書/decisions/
   ```
3. **影響マップで候補を確定する**。`docs/設計書/README.md` の表で、変わったパスに当たる行の「一緒に直す正本」を候補にする。
   表に無い変更は、**行を足す**か「影響なし: <パス>（理由）」として報告する。どちらにも落とさずに進めない。
   **書く先の文書がまだ無い**（例: 認証を触ったが 05 を足していない）ときは、足す候補として 1 行で報告し、利用者の承認を得てから `python3 scripts/add_doc.py <番号>` で足す（一覧は `--list`。索引・影響マップの行も入る）。文書を足したらフェーズが Sketch のままでないかも見る（Build の目安。切り替えは `update-overview` スキル）
4. **決まったことを 1 行拾う（ソース・打合せ記録・ADR を Read してから。推測で書かない）**。問いは「矛盾しないか」ではなく「**この変更で何が決まったか**」。次の 4 つを順に当てる。
   - 選んだ方式・構成（例: 認証は login / logout / current_user の 3 関数に分けた）
   - 置いた境界・約束（例: 資格情報はコードに持たず `.env` から読む。値の所在は `環境情報.md`）
   - 決めずに仮置きしたもの（例: SSO の方式 → 課題を起票して本文に「（未決 QA-02）」。起票は `task` スキル、ID は `new.py` の出力の 1 行目から写す）
   - 採らなかった案と理由（あれば。04 §4 か課題の過去の経緯へ）

   **決めたこと自体の正本は課題の `## 決定`**（`new.py … --decided` で起票してすぐ閉じる）。設計書には「今どうなっているか」を書き、「（決定 QA-03）」と ID を添える。
   当たったものを、影響マップの候補の該当節に 1 行ずつ足す。節が雛形のまま（空欄と例示だけ）なら、例示を消して 1 行書く。状態列のある表には `決定` / `提案` / `実装済（根拠パス）` を付ける。
   すでに書いてある記述が、この変更で事実と違うものになったら直す（「差分を知らない人が正本だけを読んだとき、事実と違うことを信じるか」）。
   4 つのどれにも当たらない（リネーム・整形・テストの追加だけ等）ときだけ「影響なし: <パス>（理由）」と報告する。**「雛形のままで矛盾しないので修正不要」は判定に使わない。**

   例（ログインの雛形を作った場合）: 05 §3 に「認証は login / logout / current_user の 3 関数に分ける（実装済: src/auth/login.py）。方式は（未決 QA-02）。資格情報はコードに持たず環境情報.md の値を .env から読む（決定）」
5. **直した文書だけ、メタ行と改訂履歴を更新する**
   - 最終更新: 今日。`（<ID>: 要点）` はタスク ID と 1 句
   - 対象: この文書が依存するソースの glob（`・` 区切り）。ソース非依存なら `案件情報.md §1・打合せ記録`
   - `repo@$(git rev-parse --short HEAD)`（ソース依存の文書のみ）
   - `## 改訂履歴` の先頭に 1 行
   - メタ行に `雛形のまま` の印があれば外す（未記入の数から外れる）
6. **下流を同じ作業で合わせる**
   - `docs/プロジェクト概要.html` → `update-overview` スキル（「直近の決定」などの自動欄は `build.py` が作るので手で書かない）
   - `案件情報.md`（関係者・実名の待ち） → `update-env-info` スキル
   - `CLAUDE.md` §5（技術スタック）・§6（用語） → 直接編集
   - ADR を足したら `docs/設計書/decisions/README.md` の索引
   - 打合せ記録の決定は課題の ID を指す（`→ QA-03`）。その課題の `## 決定` の落ち先を `→ 反映済: NN §n` に（`→ 候補: NN §n` だったものも書き換える）。旧い形の行（`→ 反映済: NN §n`）はそのままでよい
7. **検査する**
   ```bash
   python3 scripts/check_skeleton.py --docs
   python3 scripts/docs_freshness.py
   python3 scripts/check_drops.py
   ```
   NG・警告が出たら直してから終える。
8. **3 行で報告する**: 拾った 1 行（`<文書 §> <要約>`。複数なら件数と代表）/ 影響なしと判断した変更（理由）/ 影響マップに足した行

## 決めごと

- 「対象」の glob は影響マップの 1 列目と揃える。設計書が見ているソースと hook が見ているソースを一致させる
- メタ行の sha はコミット後に取る（未コミットの差分を「反映済み」にしない）。コミット前に直すときは、コミットしてから sha を書き直す
- 時点の状態（「実装済み」「検討中」）を本文に残さない。状態はタスク md、未決は課題 md（本文には「（未決 <ID>）」だけ）
- 1 件のために節を丸ごと書かない。1 行で足りる
- 影響マップの行を足すときは、同じ glob を `docs_freshness.py` の「対象」にも使えるか確かめる（`git diff -- <glob>` で引けるか）

## 禁止事項

- ソース・打合せ記録を読まずに設計書を直す（推測で書かない）
- 雛形のまま・矛盾しないことを理由に、何も書かずに終える（手順 4 の 4 つを当てる）
- メタ行だけ更新して本文を直さない。本文だけ直してメタ行・改訂履歴を更新しない
- 日付別ファイルや `_v2` を作る（同じファイルを更新し、履歴は改訂履歴と git に残す）
- 未決の論点を決定事項として書く（課題を起票して「（未決 <ID>）」）。`## N. 未決` 節に論点を書き足す
- 起票前に ID を予想して書く
- 影響マップに無い変更を黙って通す（行を足すか「影響なし」を報告する）
- `check_skeleton.py --docs` を通さずに終える
- 秘密（URL・ID・鍵）や実名を設計書に書く（`環境情報.md`・`案件情報.md` を参照させる）
