# タスク・課題・画面管理ツール 詳細仕様

> 人が最初に読むのは `README.md`（1 画面の要約）。ここは md のスキーマ・本文の雛形・領域・画面・
> 概要 HTML との連動・data.js の契約の正本。`task` スキルと CLI（`new.py`・`close.py`・`screen.py`・`build.py`）はこの仕様に従う。

## md ファイルのスキーマ（タスク）

各ファイルは先頭にフロントマターを持ちます。

```markdown
---
id: QA-03
title: ログイン画面のバリデーション追加
area: 横断
kind: タスク
status: 未着手
priority: 高
epic:
owner:
due:
tags: [0527]
screens: [SCR-01]
source:
created: 2026-06-28
updated: 2026-06-28
closed:
---

（ここから下が Markdown 本文）
```

### フロントマター各項目

| フィールド | 必須 | 説明 | 許可値 / 形式 |
|-----------|:----:|------|--------------|
| `id`      | ✅   | タスク ID（プレフィックス-連番） | `QA-01`、`DOC-03` など |
| `title`   | ✅   | タスクのタイトル | 自由文字列 |
| `area`    | ✅   | 担当領域 | `areas.json` に登録済みの名前（下の「領域と ID のプレフィックス」） |
| `kind`    | —   | 分類（省略時は `タスク`） | `タスク` / `課題`（課題＝意思決定待ちの未決事項。決着でクローズ） |
| `status`  | ✅   | 進行状態 | `未着手` / `進行中` / `方針確定` / `確認待ち` / `保留` / `完了` |
| `priority`| ✅   | 優先度 | `最高` / `高` / `中` / `低` |
| `decider` | —   | 決めるロール（課題だけ） | `SH-02` など 03 のロール ID 推奨。未整備なら「発注側」等の役割名。実名は書かない |
| `epic`    | —   | 大きな括り（エピック） | 自由文字列（省略可）。`<PREFIX>-00` の ID を持つタスクがエピック親 |
| `owner`   | —   | 担当者名 | 自由文字列（省略可） |
| `due`     | —   | 期限（タスク・課題共通） | `YYYY-MM-DD` または空。空でなく日付形式でなければ `build.py` が警告（`--check` で exit 1）。書いたものだけが一覧と概要 HTML「次の節目」に出る |
| `tags`    | —   | タグ（複数可） | `[0527, 0618]` 形式、空は `[]` |
| `screens` | —   | 関連する画面 ID（複数可） | `[SCR-01, SCR-02]` 形式、空は `[]`。省略可 |
| `source`  | —   | 元ネタファイル名 | 自由文字列（省略可） |
| `created` | —   | 作成日 | `YYYY-MM-DD` |
| `updated` | —   | 最終更新日 | `YYYY-MM-DD` |
| `closed`  | —   | クローズ日（OPEN タスクは空） | `YYYY-MM-DD` または空 |

> `new.py` が書く並びは `id, title, area, kind, status, priority, decider（課題だけ）, epic, owner, due, tags, screens, source, created, updated, closed`。

> `state`（`"open"` / `"closed"`）は `data.js` 生成時にフォルダ名から自動付与されます。md には書きません。

### 付随資料の併置

タスク本体と同じフォルダに `<ID>_内容_YYYYMMDD.md` / `.png` / `.html` のような付随資料を置けます。
フロントマターに `id` を持たない md は `build.py` がタスクとして扱いません。`close.py` はこれらを本体と一緒に移動します。
大きいもの・生データ・機密は `.work/証跡/<ID>_内容/`（Git 管理外）に置き、タスク md から「証跡: <パス>」で名指しします。
`build.py --check` は、`open/`・`closed/` にある `<ID>_` で始まる付随資料のうち、同じフォルダに本体（その ID のタスク md）が
無いもの（孤児の添付）を警告します。

## md 本文のテンプレート（9 セクション）

フロントマター以降の本文は、次の **9 セクション構成**で書く。狙いは「タスクを開いた瞬間に "何をするか" が分かる」こと。背景・現状・経緯を上位に置くと用件が埋もれるため、**用件（概要・意義・変更点・計画）を上に、背景（経緯・参照）を下に**並べる。該当の無いセクションは「なし」と書くか省略してよい。`new.py` がこの雛形を本文に書き出す。

```markdown
## 概要
（このタスクで何をするか。1〜3行で用件だけ）

## 対応の意義（なぜやるか）
- 対応しないデメリット: …
- 対応するメリット: …
（＝優先度の根拠。ここで「やる価値」を示す）

## 対応後の変更点（利用者視点）
（利用者から見た UI/UX の変化。純粋なバックグラウンド処理のみなら「なし」）

## 対応計画の概要
- 作業項目を箇条書き（スキャンできる粒度）

## 対応計画の詳細
（各作業項目の具体。対象ファイル・データモデル・移行方針・技術判断）

## 影響・依存
（他タスク・画面・設計書・レビュー観点との関係）

## 完了条件（クローズ3条件）
- [ ] 対象環境へ適用済み
- [ ] 確認者（プロジェクトで定める）の確認
- [ ] 正本（環境情報・設計書・台帳等）への反映
（揃ったら [x]。該当しない条件は `- [x] 該当なし: 理由`。コード変更を伴わないタスクは 2 つ目だけでよい。
残ったまま close.py を実行すると警告が出る）

## 過去の経緯
（これまでの打合せ・決定の変遷。「なぜ今この結論か」）

## 参照情報
（打合せ出典・設計書・関連コミット・関連タスク ID・関連画面 ID）
```

- **完了条件はチェックリスト**: `close.py` はタスク（課題以外）の `## 完了条件` 節に `- [ ]` が残っていれば、その行を並べて警告する。閉じるのは止めない（止めるのは課題の決着の記録が無いときだけ）。番号付きの旧い形（`1. …`）は見ない
- **「完了条件」はプロジェクトで書き換える**: `new.py` の `TASK_BODY` と `README.md` の「クローズ基準」を、環境名・確認者・正本の実名に置き換える
- **経緯の扱い**: 打合せの生発言・時刻などは「過去の経緯」または「参照情報」へ。概要・計画セクションに混ぜない

### 課題の本文（7 セクション）

課題（`--kind 課題`）の雛形。title は問いの形（「〜の扱い」ではなく「〜するか」）で書く。

```markdown
## 概要
（何を決める必要があるか。1〜3 行。決まらないと何が止まるか）

## 論点
- …

## 選択肢
- 案A: …
- 案B: …
- 推奨: （あれば。理由 1 行）

## 決着条件
（誰が・何をもって決着とするか。frontmatter の decider / due と食い違わせない）

## 決定
<!-- 未決の間は空欄のまま。決着したら 1 行目に決定内容、2 行目以降に落ち先を 1 行ずつ。例:
対象は本社の正社員のみ（2026-09-30 打合せ / SH-02）
→ 反映済: 01 §3
→ APP-03
-->

## 過去の経緯
## 参照情報
```

- `## 決定` の案内は HTML コメントにする（`close.py`・`drops.py` はコメントを読まない）。見える括弧書きにすると決定の 1 行目と誤読される。
  「（…）」だけの行も決定としては読み飛ばす
- 課題を `close.py` で閉じるときは、`## 決定` の 1 行目が空でないこと、落ち先の行（`→ 反映済: 01 §3` / `→ APP-03` /
  `→ 未決 QA-02` / `→ 取り下げ: 理由`）が 1 行以上あり ID が実在することを確かめ、満たさなければ閉じずに止まる
- 落ち先の書き方の正本は `docs/案件/02_打合せ/README.md`（打合せ記録・課題の `## 決定`・pickup スキルで共通）
- 起票してすぐ閉じる（決定を記録するだけの課題）は `new.py … --decided "<決定>" --to "<落ち先>"`

## 領域と ID のプレフィックス（`areas.json`）

`new.py` は同じフォルダの `areas.json`（`{"areas": {"<領域名>": "<PREFIX>"}}`）を読んで ID のプレフィックスを決めます。
**領域の対応表は `areas.json` が唯一の正本**で、この文書や README に表を複製しません（`python3 new.py -h` で一覧が出ます）。

- プロジェクト固有の領域は `areas.json` に追記するか、起票時に `--add-area 名前:PREFIX` を付ける（PREFIX は `[A-Z][A-Z0-9]*`、重複は止める）
- `area` に登録済みのプレフィックス（`APP`・`qa` など。大文字小文字は問わない）を渡すと、対応する名前に読み替えて続行する
- 未登録の area では**起票せずに止まる**（exit 2）。登録済みの一覧と追加の方法を出す
- `--add-area` は `名前:PREFIX` の順。`PREFIX:名前`（`init.py --areas` の順）も読み替える。予約接頭辞（`SH`・`ADR`・`HN`・`P`・`INV`・`SCR`・`U`）と重複は止める

### `new.py` の入力の誤り

次はすべて **exit 2 で何も作らない**（`-h` も何も作らない）。

- 未登録の area / title なし / `--due` が `YYYY-MM-DD` でない（`10/7`・`2026-13-01`）
- `--decided` だけで `--to` が無い / `--to` だけ / `--to` の ID が実在しない
- `--kind タスク` と `--decided`・`--decider` の併用
- `--add-area` の重複・予約接頭辞

補足（接頭辞の読み替え、`--kind` なしの `--decider` を課題として扱うことなど）は stderr に 1 行出す。
stdout の 1 行目は確定した ID だけ（呼び出し側はこれを読んで本文や落ち先に書く）。

## 画面（screens/）

画面ごとの実装状況を `screens/SCR-NN_<名前>.md` で管理し、タスクと相互に紐付けます。

### スキーマ

```markdown
---
id: SCR-01
name: ログイン
path: /login
status: 未着手
owner:
tags: []
created: 2026-06-28
updated: 2026-06-28
---

## 概要
（この画面の役割。誰が・何のために使うか）

## 主要な操作
- …

## 参照（設計書・タスク）
- 設計書:
- 関連タスク: タスク側の frontmatter `screens:` にこの ID を書くと build.py が逆引きする
```

| フィールド | 必須 | 説明 | 許可値 / 形式 |
|-----------|:----:|------|--------------|
| `id`      | ✅   | 画面 ID | `SCR-NN`（`screen.py new` が採番） |
| `name`    | ✅   | 画面名 | 自由文字列 |
| `path`    | —   | URL パスや画面識別子 | 自由文字列（省略可） |
| `status`  | ✅   | 実装状況 | `未着手` / `実装中` / `確認待ち` / `完了` / `保留` |
| `owner`   | —   | 担当者名 | 自由文字列（省略可） |
| `tags`    | —   | タグ | `[a, b]` 形式、空は `[]` |
| `created` / `updated` | — | 作成日 / 最終更新日 | `YYYY-MM-DD` |

### screen.py

```bash
python3 screen.py new "<名前>" [--path /x] [--owner 名前]   # 採番して作成 → build.py
python3 screen.py set <ID> <status>                          # status / updated を更新 → build.py
```

フロントマターの書き換えは `close.py` のユーティリティ（`find_md` / `rewrite_md`）を import して使っているため、
`screen.py` は `close.py` と同じフォルダに置く必要があります。

### タスクとの関連付け

- タスク側の frontmatter に `screens: [SCR-01, SCR-02]` を書く（画面側にはタスク ID を書かない）
- `build.py` がタスクの `screens:` を逆引きして、各画面の `tasks` を計算する
- 存在しない画面 ID を参照すると `build.py` が警告する（`--check` では終了コード 1）
- index.html では、タスク詳細の「画面」チップをクリックすると画面ビューのその画面へ、画面詳細の「関連タスク」を
  クリックするとタスクビューのそのタスクへ移動する（CLOSED タスクは打消し線で表示。OPEN/CLOSED フィルタで
  隠れる場合は自動で「すべて」に切り替わる）

## プロジェクト概要 HTML との連動（スナップショット）

`build.py` は `docs/プロジェクト概要.html`（このフォルダから見て `../../プロジェクト概要.html`）が存在し、
中に次のマーカー対があれば、その**内側だけ**を置き換えて書き戻します。

```html
<!-- BEGIN:task-snapshot -->
（ここが build.py のたびに差し替わる）
<!-- END:task-snapshot -->
```

埋め込む内容（`<p>` と `<table>` のみ・外部依存なし）:

- 生成時刻、OPEN / CLOSED 件数、OPEN のうち課題・確認待ち・進行中の件数
- 最高優先の OPEN タスク上位 10 件（ID・タイトル・優先度・状態・期限。課題は「決めてほしいこと」に出るので除く）
- 画面の進捗（完了 n / 全 m）

同じ要領で「3. 現在地」の次の 3 欄も書き換えます（手で編集しない）。

| マーカー | 見出し | 出典 |
|---|---|---|
| `open-issues` | 決めてほしいこと | open の課題（ID・問い・決める・期限・状態。期限の近い順 → 優先度。8 件まで） |
| `milestones` | 次の節目 | ロードマップの時期が日付の行 + open のタスク・課題の `due`（期限切れを先頭に、今日以降の近い順に 5 件） |
| `recent-decisions` | 直近の決定 | 打合せ記録の決定行 + 閉じた課題の `## 決定`（新しい順に 5 件） |

ファイルやマーカーが無い場合は注記を出して続行します（`--check` の警告数には数えません）。
`--check` では書き込みません。

## data.js の仕様（index.html との契約）

`build.py` が生成する `data.js` の形式:

```js
window.TASKS = [
  {
    "id": "QA-03",
    "title": "ログイン画面のバリデーション追加",
    "area": "横断",
    "status": "未着手",
    "priority": "高",
    "kind": "タスク",
    "epic": "",
    "owner": "",
    "due": "",
    "decider": "",
    "tags": ["0527"],
    "screens": ["SCR-01"],
    "source": "",
    "created": "2026-06-28",
    "updated": "2026-06-28",
    "closed": "",
    "state": "open",
    "body": "## 概要\n..."
  }
];
window.SCREENS = [
  {
    "id": "SCR-01",
    "name": "ログイン",
    "path": "/login",
    "status": "実装中",
    "owner": "",
    "tags": [],
    "created": "2026-06-28",
    "updated": "2026-06-28",
    "state": "screen",
    "body": "## 概要\n...",
    "tasks": [
      { "id": "QA-03", "title": "ログイン画面のバリデーション追加", "state": "open", "status": "未着手", "kind": "タスク" }
    ]
  }
];
```

- `state`: タスクは `"open"` または `"closed"`（フォルダ由来）、画面は `"screen"`。md には書かない
- `body`: フロントマター以降の生 Markdown 文字列
- `due`・`decider`: frontmatter の値（空文字可）
- `SCREENS[].tasks`: タスクの `screens:` からの逆引き（`build.py` が計算）
- ソート順: プレフィックス昇順 → 連番昇順（安定ソート）
- 日本語はそのまま（`ensure_ascii=False`）
- コミット時の初期値は `window.TASKS = []; window.SCREENS = [];`。`index.html` は `window.SCREENS` が未定義でも動く
