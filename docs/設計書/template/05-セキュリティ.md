## 0. 位置づけ

「何を・誰から・どこで守るか」の判定基準。セキュリティレビューの指摘は本書の節番号か `06-品質と確認.md` §6 の INV-xx を根拠に書く。根拠が書けない指摘は Low に落とす。

`未決`・`提案` の項目を根拠に「方針に反する」と指摘しない。`決定` に実装が反していれば実装側を直す（`04-原則.md` §3）。

## 4. データの格付けと扱い

**秘密か分からない値は秘密として扱う。** 格付けが決まるまで画面・ログ・会話出力に出さない。

| 格付け | 例 | 保存先 | 画面表示 | ログ可否 | 寿命 | 状態 |
|:--|:--|:--|:--|:--|:--|:--|
| 公開 | 公開済みの文書・画面文言 | リポ内・共有の文書置き場 | 可 | 可 | 無期限 | 決定 |
| 内部 | 設計書・タスク md・打合せ記録 | `docs/` | 関係者のみ | 可 | 無期限 | 決定 |
| 機密 | 受領した一次資料・関係者名 | `.work/機密/`・`案件情報.md` | 不可 | 不可 | 案件終了まで | 決定 |
| 秘密 | 資格情報・鍵・接続文字列 | `環境情報.md`・`.env` | 不可 | 不可（マスク必須） | ローテーションまで | 決定 |

（例）`機密 | 利用者の氏名・メール | DB の users テーブル | 本人と管理者のみ | 不可（ID のみ） | 退会後 N 日 | 提案`

## 9. Claude Code が行ってはいけない操作

`.claude/settings.json` の `permissions.deny` と対応付ける。deny に無いものは「人が見る」（`06-品質と確認.md` §3）。
状態が「決定」の行の deny 列には、`settings.json` と同じ形でパターンを書く（`python3 scripts/check_skeleton.py --harness` が deny にあるかを見る）。
deny は最善努力: パターンは前方一致なので、語順を変えた書き方は漏れる。漏れは人が見る（06 §3）。行を足すときは `harness` スキル。

| 操作 | なぜ | `permissions.deny` の対応 | 状態 |
|:--|:--|:--|:--|
| `環境情報.md`・`.env` の値を `docs/`・会話出力へ転記する | 回収できない | （hook・rules で防ぐ。`.claude/rules/secrets.md`） | 決定 |
| `--no-verify` でゲートを飛ばす | 機械の検査が無効になる（06 §8） | `Bash(git commit --no-verify *)`・`Bash(git push --no-verify *)` | 決定 |
| 本番への変更の反映・戻しを承認なしに実行する（例: 開発ならマイグレーション・デプロイ、SaaS/インフラの管理なら本番環境の設定変更） | 07 §4〜§6 の承認手順の外 | （コマンドが案件ごとに違う。案件の本番操作が決まった時点で `harness` スキル（観点「危険操作」）で deny に足す。Build への切り替え時の見直しで必ず確かめる） | 決定 |
| 履歴の破壊（force push・reset --hard・clean・バックアップ削除） | 戻せない | `Bash(git push --force *)`・`Bash(git push -f *)`・`Bash(git push --force-with-lease *)`・`Bash(git reset --hard *)`・`Bash(git clean -f *)` | 決定 |
