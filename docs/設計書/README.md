# docs/設計書/ — 設計の正本

この仕事の設計・方針を示す恒久ドキュメント。**詳細はコード・設定が正本**で、設計書は概要・方針にとどめる。スリムに保つ（1 本 80〜150 行）。
時点の状態（いまどこか・何が動いているか）は持たない。それは `docs/プロジェクト概要.html`・タスク md・`案件情報.md` の仕事。**決まったことの正本は課題 md の `## 決定`**。設計書は「今どうなっているか」を書き、根拠として決定の ID を指す（例「社内 SSO（決定 QA-03）」）。

**設計書は育てる。** 最初は `01-概要.md` だけ。ほかの文書（構成・関係者・原則・セキュリティ・品質と確認・変更と反映・利用者の運用・非機能と障害時）は `template/` にあり、必要になったら候補を出し、承認を得てから `python3 scripts/add_doc.py <番号>` で足す（一覧は `--list`）。足すと、下の 4 つの表に行が入る。

## 変えたもの → 一緒に直す正本

**同じ作業の中で直す。** 表に無いものを変えたら、行を足すか「影響なし」を理由付きで報告する。どちらにも落とさずに進めない（`sync-design-docs` スキル）。1 列目のバッククォート内は変更パスの glob（複数は `・` 区切り）、2 列目のバッククォート内は直す文書（左から順に。入れ子の別リポの中の文書はそのリポからの相対でもよい）。バッククォートで glob を囲んだ行は hook と `scripts/check_skeleton.py` が機械で読む。glob の無い行は人向け。同じ glob の行が複数あれば、hook は当たった行をすべて合わせて出す（文書を足すと、その文書の行が増える）。表で書きにくい判定は差し込み口 `.claude/hooks/impact_map_local.py` に書け、置いたら表にそれを指す行を足す（`sync-design-docs` スキル）。

## 書き方

全設計書に共通。詳細は `.claude/rules/docs-management.md` の「設計書の書き方」。

- **冒頭**: `# NN タイトル — 一言` の直後に引用ブロック 3 行。1 行目は鮮度メタ（機械が読む。正確にこの形）: `> 最終更新: YYYY-MM-DD（<タスクID>: 要点）／ 対象: <追随するソースの glob を・区切り> / repo@<short-sha>`。対象が `.claude/project.json` の `nested_repos`（入れ子の別リポ）の中なら、その sha を `・<リポ名>@<short-sha>` で並べる（例 `/ repo@abc1234・sub-repo@def5678`）。ソースに依存しない文書は `対象: 案件情報.md §1・打合せ記録`（`repo@` 省略）。任意で末尾に ` ／ 鮮度: 90日`。雛形の初期値は `> 最終更新: 2026-10-01（初版。雛形のまま）／ 対象: —`。2 行目 `> 作成: YYYY-MM-DD ／ 位置づけ: 〈何の正本か〉 ／ 対象読者: Claude Code・担当者`。3 行目 `> 扱わないもの: X → \`参照先\`、Y → \`参照先\``
- **§0 位置づけ** に固定文を置く: 「`未決`・`提案` の項目を根拠に『方針に反する』と指摘しない。`決定` に反していれば、実装・設定の側を直す」
- **表には「状態」列**を持つ。値は 決定 / 実装済 / 提案 / 未決。`決定` には決定の ID を添える（例「決定（QA-03）」）。`実装済` は根拠パス必須
- **未決は本文に書かない。** 未決の正本は課題 md（`docs/案件/01_タスク管理/`、kind=課題。`new.py <area> "<問いの形>" --kind 課題`）。本文の決まっていない箇所には「（未決 QA-01）」のように**起票した課題の ID** を書く（起票前に ID を予想して書かない）。決まったら「（決定 QA-01）」に書き換える。末尾の `## N. 未決` は固定文 1 行のまま書き足さない。本書に関わる未決の一覧は `python3 scripts/check_drops.py --refs NN`
- **末尾に `## 改訂履歴`**（表: 日付 / 内容 / 関連 ID。新しい順）。本文を変えたら同じ日に 1 行足し、鮮度メタの最終更新を合わせる
- **書かないもの**: タスク ID・SHA・進捗（「（未決 ID）」「（決定 ID）」の参照・改訂履歴・鮮度メタ以外）、秘密の実値、実名。日付別・`_v2` ファイルは作らない（退避は `.work/_bk/`）
- **ID 体系**: P-（原則）、SH-（関係者ロール）、INV-（不変条件）、SCR-（画面。`docs/案件/01_タスク管理/screens/`）。未決・決定は課題の ID（`areas.json` のプレフィックス。例 QA-01）で、設計書ごとの採番はしない
- **初期状態**: 各節は「空欄の表 or 箇条書き ＋ 括弧書きの例示 1 行」。例示は埋めたら消す
- **未記入の扱い**: 鮮度メタ行が雛形の初期値（`雛形のまま`）の文書は「未記入」と数える（Sketch では件数だけ、Build では警告。止めない）。節を 1 行でも埋めてメタ行を書き換えれば未記入でなくなる
- 実装・設定と食い違ったら、まず設計書側で「どちらが正か」を確定してから下流を合わせる
